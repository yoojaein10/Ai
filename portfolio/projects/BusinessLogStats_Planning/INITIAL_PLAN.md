# 업무일지 통계 통합 화면 초기 계획

- 문서 상태: 초기 계획
- 작성일: 2026-07-23
- 현재 범위: `SP_IW_S_TaskStats_Mon` 기반 월별 통계 화면 1개
- 제외 범위: 상위 보고서 탭 및 추가 보고서 구현

## 1. 목표

동일한 업무일지 통계를 아래 두 경로에서 제공한다.

1. 데스크톱 EXE
2. 모바일 웹

데스크톱과 모바일은 서로 다른 사용자 식별값을 받지만, 서버에서
`TMWCMN_USR_BAC_INFO`의 동일 사용자 행으로 변환하여 같은 데이터와 권한을
제공한다.

| 진입 경로 | 수신 식별값 | 사용자 조회 기준 |
|---|---|---|
| 데스크톱 EXE | `USR_SEQ` | `TMWCMN_USR_BAC_INFO.USR_SEQ` |
| 모바일 웹 | `USR_ID` | `TMWCMN_USR_BAC_INFO.USR_ID` |

`USR_SEQ`와 `USR_ID`는 사용자를 찾기 위한 식별값으로만 사용한다. 식별값
자체를 로그인 또는 권한 증명으로 신뢰하지 않는다.

## 2. 1차 구현 범위

### 포함

- `SP_IW_S_TaskStats_Mon` 실행 결과 조회
- 연도·월 조회 조건
- 담당자별 핵심 요약
- 담당자 선택 시 전체 상세 항목 표시
- 표시 항목 선택
- 전체 컬럼 보기
- 데스크톱과 모바일 반응형 화면
- 사용자 식별값 변환 및 권한 확인

### 제외

- 유치자별, 처리자별 등 다른 보고서
- 화면 상단의 보고서 탭
- 신규 프로시저 작성
- 기존 프로시저 수정
- 엑셀 다운로드
- 관리자용 사용자 매핑 편집 화면

## 3. 화면 정보 구조

모든 원본 컬럼은 유지하되 처음부터 한 화면에 전부 펼치지 않는다.

### 3.1 기본 화면

1. 화면 제목 및 로그인 사용자 표시
2. 연도·월 조회 조건
3. 월간 요약
4. 담당자별 핵심 요약표
5. 선택한 담당자의 상세 내역

담당자별 핵심 요약표의 기본 컬럼은 다음과 같다.

| 컬럼 | 설명 |
|---|---|
| 담당자 | 담당자 선택 및 상세 조회 |
| 총 투입시간 | 시간 기반 항목의 합계 |
| 투입금액 | 시간 기반 항목의 금액 합계 |
| 처리건수 | 건수 기반 항목의 합계 |
| 처리금액 | 건수 기반 항목의 금액 합계 |
| 총 산정금액 | 투입금액과 처리금액의 합계 |

총계는 원본 컬럼을 대체하지 않는 요약 표시다. 서로 다른 처리 단계의 건수를
합산하면 동일 문서가 중복 포함될 수 있으므로, `처리건수`와 `총 산정금액`의
업무상 의미는 구현 전에 확인한다.

### 3.2 표시 항목 선택

보고서 탭 대신 `표시 항목` 선택 컨트롤을 사용한다.

- 요약
- 인력 투입
- 기본 처리
- 탁상 업무
- 특수 업무
- 비용
- 전체 컬럼

각 항목을 선택하면 담당자별 비교표의 컬럼 구성이 변경된다. 시간 기반 항목은
항상 `시간/금액`, 건수 기반 항목은 항상 `건수/금액` 쌍으로 표시한다.

### 3.3 담당자 상세

담당자를 선택하면 해당 담당자의 모든 원본 항목을 아래 상세 영역에 표시한다.

- 데스크톱: 표 아래 상세 패널
- 모바일: 접기/펼치기 상세 영역

사용자는 기본 표에서 전체 현황을 비교하고, 필요한 담당자만 선택하여 세부
시간·건수·금액을 확인할 수 있다.

### 3.4 전체 컬럼 보기

감사, 대조 및 기존 화면과의 비교를 위해 모든 컬럼을 펼치는 기능을 제공한다.

- 첫 번째 담당자 컬럼은 식별하기 쉽게 유지
- 가로 스크롤 허용
- 시간/금액 및 건수/금액 쌍의 순서를 고정
- 숫자는 우측 정렬
- 0, 시간, 건수, 금액의 표시 형식을 통일
- 모바일에서는 상세 영역 사용을 기본으로 하고 전체 컬럼 보기는 보조 기능으로 제공

### 4.6 데이터 계약 확인 결과 (2026-07-23, DB 실물 대조 완료)

프로시저 정의와 샘플 실행(2026-06, 2024-06)으로 확인했다. 원문은
`SP_IW_S_TaskStats_Mon.sql` 참조.

- 파라미터: `@F_Date varchar(10)` (앞 7자리 `YYYY-MM`만 사용),
  `@Manager varchar(10)` (빈 값이면 전체, 값이 있으면 해당 담당자 1명).
- 결과: 담당자당 1행, 총 45컬럼. §4.1~4.5의 컬럼명이 실물과 일치하며
  `SuPrice`가 실제 컬럼명이다(`SuPPrice` 아님).
- **컬럼 순서가 연도 분기(`@StandYear` 2025 전/후)에 따라 다르다.**
  `KBYAKC/KBYAKP` 위치가 달라지고 `HugJup_Price` 등의 자료형도 달라진다.
  클라이언트는 반드시 컬럼명 기준으로 매핑하고 순번(ordinal)을 쓰지 않는다.
- 자료형: 시간 컬럼(`M1Time` 등 4개)은 `"시:분"` 형식의 **문자열**이다.
  총 투입시간 합계를 내려면 서버에서 파싱해야 한다. 인력투입 금액은
  float, 나머지 금액은 decimal(money), 건수는 int.
- `CHKC`/`CHKP`(검산)는 현재 프로시저에서 항상 0으로 고정되어 있다
  (집계 로직이 주석 처리됨). 화면에서 숨기거나 0 표시 정책을 정한다.
- KB 약식은 `'김형수'`, HUG 탁상은 `'안창덕'`으로 담당자가 프로시저에
  하드코딩되어 있다.
- 담당자 행의 모집단은 `Seat_UserInfo`의 team `P1/J1/P2` + 전화번호 보유자
  이며(샘플 월 기준 79명), 모든 집계가 담당자 **이름**으로 조인된다.
  동명이인이 생기면 집계가 합쳐지는 구조임을 인지한다.
- `@F_Date`와 `@Manager`는 프로시저 내부에서 `LIKE` 패턴에 직접 쓰이므로,
  서버에서 `YYYY-MM` 형식 검증과 와일드카드 문자(`%`, `_`, `[`) 차단을
  반드시 수행한다.

## 5. 사용자 식별 및 권한 처리

### 5.1 데스크톱 EXE

1. EXE는 최초 실행 시 서버 인증을 거쳐 세션 토큰을 발급받는다.
   `USR_SEQ` 단독 전달을 인증으로 인정하지 않는다.
2. 이후 통계 요청은 토큰으로 인증하고, 서버가 토큰에 연결된
   `TMWCMN_USR_BAC_INFO.USR_SEQ`로 사용자를 조회한다.
3. 요청에 포함된 `USR_SEQ`는 무시하거나 토큰의 값과 일치할 때만 허용한다.
4. 활성 사용자, 소속, 사무소 및 기능 권한을 확인한다.
5. 확인된 서버 측 사용자 컨텍스트로 통계 화면을 제공한다.

### 5.2 모바일 웹

1. 기존 웹 로그인 세션에서 `USR_ID`를 가져온다.
2. 요청 파라미터의 `USR_ID`는 사용하지 않는다. 세션이 없거나 만료된
   요청은 거부한다(fail-closed).
3. 서버가 세션의 `USR_ID`로 `TMWCMN_USR_BAC_INFO`를 조회한다.
4. 데스크톱과 동일한 사용자 컨텍스트와 권한 규칙을 적용한다.

### 5.3 공통 원칙

- 이름을 사용자 매핑 키로 사용하지 않는다.
- 비활성·퇴사 사용자는 접근을 차단한다.
- 중복되거나 매핑되지 않는 ID는 임의로 추정하지 않는다.
- 화면과 브라우저에서 DB에 직접 연결하지 않는다.
- DB 계정에는 필요한 프로시저 실행 권한만 부여한다.
- 조회 조건과 사용자 권한은 서버에서 재검증한다.
- 통계 접근 기록에는 사용자, 조회 월, 결과 상태를 남긴다.
- 로그에는 인증 토큰과 불필요한 개인정보를 기록하지 않는다.
- 모든 구간은 HTTPS로 통신한다.
- 연도·월 등 조회 조건은 서버에서 형식·범위를 검증하고, 프로시저 호출 시
  파라미터 바인딩만 사용한다(문자열 조립 금지).
- 통계 조회 가능 범위(본인만/부서/전체 담당자)를 역할 기준으로 정의하고,
  서버에서 강제한다. 1차 구현 전 업무 담당자가 확정한다.
- 인증 실패·권한 없음 응답은 존재 여부를 노출하지 않는 동일한 형식으로
  반환한다. 로그와 내부 상태 코드에서만 원인을 구분한다.

## 6. 공통 서비스 구조

```text
데스크톱 EXE -- USR_SEQ --┐
                          ├─ 사용자 확인/권한 ─ 통계 API ─ MSSQL 프로시저
모바일 웹 ---- USR_ID ----┘
```

두 화면은 동일한 통계 API와 표시 규칙을 사용한다. 진입 경로별로 사용자
식별값을 해석하는 부분만 분리한다.

## 7. 향후 보고서 확장 원칙

1차 화면에는 보고서 탭을 표시하거나 구현하지 않는다. 다만 다음 요소는
나중에 보고서를 추가할 수 있도록 분리한다.

- 조회 조건 영역
- 사용자 컨텍스트
- 보고서별 API 호출
- 컬럼 정의
- 담당자 상세 구성
- 보고서별 접근 권한

향후 보고서를 추가할 때 각 보고서는 다음 정의를 갖도록 계획한다.

| 정의 | 설명 |
|---|---|
| 보고서 ID | 내부 고유 식별자 |
| 표시명 | 메뉴 또는 탭에 표시할 이름 |
| API | 보고서 데이터 조회 경로 |
| 필터 | 연도·월 등 조회 조건 |
| 컬럼 그룹 | 요약·시간·건수·금액 구성 |
| 상세 구성 | 담당자 또는 문서 상세 항목 |
| 권한 | 접근 가능한 역할·부서 |

상위 보고서 탐색 UI는 실제 두 번째 보고서가 확정된 이후 추가한다.

## 8. 단계별 진행 계획

### 1단계: 데이터 계약 확정

- 프로시저 반환 컬럼과 자료형 확인 — **완료(§4.6)**
- 시간, 건수, 금액의 표시 형식 확정
- `구분 2` 항목의 업무 명칭 확정 (분기 기준은 확인됨, 명칭만 남음)
- 총계에 포함할 항목과 중복 가능성 확인
- 샘플 월을 기준으로 기존 화면과 값 대조

### 2단계: 사용자 흐름 확정

- EXE의 `USR_SEQ` 전달 방식 확인
- 모바일 세션의 `USR_ID` 저장 위치 확인
- 동일 사용자에 대한 두 식별값 매핑 검증
- 권한 없음, 퇴사, 매핑 실패 처리 정의

### 3단계: 화면 시안 확정

- 기본 요약표
- 표시 항목 선택
- 담당자 상세
- 전체 컬럼 보기
- 데스크톱·모바일 레이아웃

### 4단계: 공통 API 설계

- 요청·응답 형식
- 날짜 및 사용자 권한 검증
- 프로시저 실행 정책
- 오류·빈 결과 처리
- 감사 로그

### 5단계: 연동 및 검증

- 데스크톱 EXE 메뉴 연결
- 모바일 웹 메뉴 연결
- WebView2 및 모바일 브라우저 확인
- 기존 화면과 결과 비교
- 일부 사용자 시범 운영

## 9. 검증 기준

- 동일 사용자가 EXE와 웹에서 같은 권한과 데이터를 받는다.
- 모든 프로시저 결과 컬럼을 상세 또는 전체 보기에서 확인할 수 있다.
- 시간과 금액, 건수와 금액이 서로 합쳐지거나 누락되지 않는다.
- 기본 화면에서 담당자 간 핵심 수치를 쉽게 비교할 수 있다.
- 모바일 화면에서 전체 컬럼을 강제로 읽지 않아도 상세 조회가 가능하다.
- 매핑 실패, 권한 없음, 빈 결과가 로그·내부 상태 코드에서 명확하게
  구분된다. 단, 클라이언트 응답은 5.3의 통일 형식을 따른다.
- 기존 화면과 표본 데이터의 컬럼별 값이 일치한다.

## 10. 구현 전 확인 사항

- `USR_SEQ`와 `USR_ID`의 유일성 및 활성 사용자 조건
- 모바일 웹 세션에서 신뢰할 수 있는 `USR_ID` 취득 방법
- 데스크톱 EXE의 서버 인증·토큰 발급 방식(기존 로그인 재사용 여부)

- 항목별 총계 계산 가능 여부
- 데스크톱 `/desktop` 서버 소스 및 배포 담당
- 모바일 JSP 소스 및 배포 담당
- 새 화면의 최종 URL과 메뉴 명칭
