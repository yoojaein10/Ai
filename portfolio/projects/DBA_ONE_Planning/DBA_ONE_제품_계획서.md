## 1. 제품 정의

### 1.1 한 문장 정의

DBA ONE은 데이터베이스를 24시간 관찰하고 문제를 진단하며, 수정안을 테스트한 뒤 승인 절차에 따라 실행하고 결과까지 검증하는 AI DBA 플랫폼이다.

### 1.2 해결하려는 문제

- 여러 DB 서버의 상태와 장애를 한눈에 파악하기 어렵다.
- 느린 쿼리나 프로시저를 발견해도 원인과 영향 범위를 찾는 데 시간이 오래 걸린다.
- 테이블·뷰·프로시저 간 의존성이 복잡해 변경 위험을 판단하기 어렵다.
- 사용되지 않는 객체를 정리하고 싶어도 사용 이력의 신뢰도가 불명확하다.
- 숙련된 DBA가 부족하거나 특정 담당자에게 운영 지식이 집중된다.
- 진단 도구, SQL 편집기, 배포 승인, 감사 기록이 서로 분리돼 있다.
- 장애 당시의 실행 계획·대기·잠금·배포 기록을 함께 비교하기 어렵다.

### 1.3 제품이 제공하는 가치

- 전체 DB 상태와 중요한 문제를 우선순위별로 요약한다.
- 문제의 증상뿐 아니라 원인, 근거, 영향 범위와 해결안을 함께 제시한다.
- 프로시저 생성·수정·삭제를 하나의 안전한 변경 절차로 통합한다.
- AI 챗봇을 자연어 인터페이스로 제공하되 직접 실행 권한은 정책으로 제한한다.
- 변경 전 테스트, 승인, 적용, 사후 검증과 롤백을 하나의 기록으로 남긴다.
- 숙련된 DBA의 판단 과정을 표준화해 조직의 운영 지식으로 축적한다.

### 1.4 제품 포지셔닝

단순 DB 모니터링 제품이나 SQL 편집기가 아니라 다음 세 영역을 결합한다.

1. **관제:** 서버·세션·쿼리·잠금·대기 상태의 상시 모니터링
2. **분석:** 객체 구조, 실행 계획, 사용 이력, 성능 회귀와 영향 범위 분석
3. **안전한 실행:** 변경안 생성, 테스트, 승인, 배포, 검증, 롤백

## 2. 제품 원칙

### 2.1 핵심 원칙

1. 관찰과 진단은 최대한 자동화한다.
2. AI의 결론에는 항상 측정 근거와 신뢰도를 표시한다.
3. 운영 변경은 위험도에 맞는 승인 절차를 거친다.
4. 읽기 권한과 변경 권한을 물리적·논리적으로 분리한다.
5. 변경 전후 결과와 성능을 비교할 수 없으면 자동 적용하지 않는다.
6. 사용자가 이해하기 쉬운 표현을 먼저 보여주고 전문 데이터는 상세 화면에 둔다.
7. DB별 차이와 라이선스 제한을 숨기지 않는다.
8. 모든 작업은 누가, 언제, 무엇을, 왜 수행했는지 추적할 수 있어야 한다.
9. DB에서 수집한 코드·주석·데이터는 AI 명령이 아닌 신뢰할 수 없는 분석 자료로 취급한다.
10. 수집 에이전트 자체가 DB 성능에 부담을 주지 않도록 제한한다.

### 2.2 AI 자동화 수준

| 수준 | 설명 | 기본 정책 |
|---|---|---|
| L0 관찰 | 메타데이터와 성능 상태 수집 | 자동 |
| L1 진단 | 이상 감지, 원인 후보와 근거 제시 | 자동 |
| L2 제안 | SQL·인덱스·운영 조치안 생성 | 자동 생성, 사용자 검토 |
| L3 검증 | 테스트 환경 실행 및 결과 비교 | 승인된 범위에서 자동 |
| L4 운영 실행 | 프로시저 변경, 인덱스 생성, 세션 종료 | 권한자 승인 필수 |
| L5 긴급 자동 조치 | 사전 승인된 제한적 런북 실행 | 향후 기능, 기본 비활성화 |

### 2.3 제품이 하지 않는 것

- 근거 없이 객체가 미사용이라고 단정하지 않는다.
- AI가 임의로 운영 관리자 권한을 보유하지 않는다.
- 운영 데이터를 고객 동의 없이 외부 AI 서비스로 전송하지 않는다.
- 성능 향상을 이유로 업무 결과가 달라지는 SQL을 자동 배포하지 않는다.
- 라이선스가 확인되지 않은 Oracle 유료 진단 기능을 자동 사용하지 않는다.
- 백업·복원 전략 없이 파괴적 변경을 실행하지 않는다.

## 4. 지원 범위 전략

### 4.1 1차 지원: Microsoft SQL Server

초기 제품 완성도를 높이기 위해 MSSQL을 우선 지원한다.

- 서버·인스턴스·데이터베이스 탐색
- 테이블, 뷰, 프로시저, 함수, 트리거, 인덱스 메타데이터
- Query Store 기반 실행 이력과 계획 회귀 분석
- DMV 기반 세션, 대기, 잠금, I/O 상태
- 프로시저 CREATE, ALTER, DROP 워크플로
- 실행 계획 비교와 인덱스 후보 분석
- SQL Agent 작업과 배치 연계 정보

### 4.2 2차 지원: Oracle Database

- CDB/PDB와 스키마 구조 반영
- 패키지, 프로시저, 함수, 뷰, 시퀀스, 트리거 지원
- 세션, wait event, lock, SQL 통계 분석
- AWR·ASH·ADDM 등 사용 시 고객 라이선스 확인 및 기능 게이트 적용
- Edition, RAC, Data Guard, 멀티테넌트 여부에 따른 기능 차이 표시
- PL/SQL 컴파일 오류와 의존성 상태 지원

### 4.3 3차 지원: PostgreSQL

- pg_stat_statements 기반 쿼리 통계
- 함수·프로시저·뷰·인덱스·잠금 분석
- autovacuum, bloat, replication 상태 진단

### 4.4 어댑터 원칙

공통 UI와 승인 흐름은 유지하되 수집 쿼리, 권한, 분석 규칙과 변경 문법은 DB별 어댑터로 분리한다.

## 5. 전체 정보 구조

### 5.1 주 메뉴

1. **홈** — 조직 전체 DB 상태 요약
2. **모니터링** — 서버·쿼리·프로시저·세션·잠금 실시간 관제

5. **변경 승인** — 요청, 테스트, 승인, 배포, 롤백
6. **AI DBA** — 자연어 질의와 작업 지시
7. **알림 센터** — 알림 정책, 수신 채널, 이력
8. **감사 로그** — 접속·조회·AI·실행·승인 기록
9. **설정** — 연결, 수집, 권한, 보존, AI, 보안 정책

### 5.2 사용자 이동 흐름

```text
전체 상태
  → 이상 서버/DB 선택
  → 느린 쿼리·잠금·리소스 원인 확인
  → 관련 프로시저 또는 객체 열기
  → AI 분석 및 수정안 생성
  → 테스트와 영향 범위 검증
  → 승인 요청
  → 운영 적용
  → 사후 성능 확인
  → 정상화 또는 롤백
```

## 6. 화면별 상세 기획

## 6.1 최초 연결 및 온보딩

### 목적

사용자가 DB 종류를 선택하고 최소 권한으로 안전하게 연결하도록 안내한다.

### 구성

- DB 종류: MSSQL, Oracle, PostgreSQL
- 연결 방식: 직접 연결, 고객망 에이전트, SSH 터널, 프록시
- 환경 구분: 개발, 테스트, 스테이징, 운영
- 서버 별칭과 업무 서비스명
- 호스트·포트·인스턴스 또는 서비스명
- 인증 방식과 비밀 저장소 선택
- TLS 인증서 검증 옵션
- 읽기 전용 진단 계정 테스트
- 변경 실행 계정 별도 등록
- 접근 가능한 데이터베이스 선택
- 수집 항목과 예상 부하 미리보기
- Query Store 등 필요한 기능 상태 확인
- Oracle 관리 팩 라이선스 확인 질문
- 연결 테스트 결과와 누락 권한 안내

### 안전 기준

- 비밀번호를 로그·URL·설정 파일에 평문 저장하지 않는다.
- 연결 테스트 시 쓰기 명령을 실행하지 않는다.
- 운영 DB 연결은 화면 전체에 고정 배지로 표시한다.
- 인증서 검증 해제는 보안 관리자 승인과 경고가 필요하다.

## 6.2 홈 대시보드

### 목적

30초 안에 전체 DB 상태와 가장 중요한 문제를 파악한다.

### 핵심 카드

- 전체 서버: 정상, 주의, 위험, 연결 끊김
- 오늘 발생한 인시던트와 미해결 건수
- 성능이 악화된 프로시저·쿼리 수
- 장시간 Blocking과 Deadlock
- 저장공간·로그·백업 위험
- 승인 대기 변경
- 수집 지연 또는 에이전트 이상

### 우선순위 영역

- 지금 조치가 필요한 문제
- 업무 영향이 큰 문제
- 최근 배포 이후 발생한 성능 회귀
- 반복되는 문제와 근본 원인 후보
- AI가 추천하는 오늘의 점검 항목

### 표시 원칙

- 정상은 간결하게, 위험은 근거와 업무 영향을 함께 표시한다.
- 서버 지표보다 서비스 영향이 먼저 보이게 한다.
- 운영·테스트·개발 환경을 색상과 텍스트로 동시에 구분한다.

## 6.3 실시간 모니터링

### 목적

현재 DB 상태와 최근 변화, 이상 징후를 한 화면에서 관찰한다.

### 상단 필터

- 조직 / 서버 그룹 / DB 종류 / 인스턴스 / DB / 환경
- 시간 범위: 실시간, 15분, 1시간, 24시간, 7일, 사용자 지정
- 정상·주의·위험 필터
- 기준선 비교: 이전 기간, 전일 동일 시간, 전주 동일 시간

### 서버·DB 지표

- CPU, 메모리, 연결 수와 활성 세션
- 데이터·로그 파일 사용량과 증가 추세
- I/O 지연, 처리량과 대기 큐
- 컴파일, 재컴파일, 캐시 상태
- 트랜잭션 처리량과 장기 트랜잭션
- TempDB 또는 임시 영역 사용
- 복제·가용성·백업 상태
- 에이전트 수집 지연과 누락

### 쿼리·프로시저 지표

- 평균, P50, P95, P99, 최대 실행시간
- 호출 횟수, 실패 횟수, 타임아웃
- CPU, 논리 읽기, 물리 읽기, 쓰기
- 반환 행 수와 예상 행 수 차이
- 실행 계획 변경과 성능 회귀
- wait category 및 주요 병목
- 파라미터별 성능 편차
- 평소 대비 이상 점수

### 잠금·세션 영역

- Blocking Tree
- Blocker와 Waiter 관계
- 잠금 지속시간과 영향 세션 수
- 장기 실행 세션
- Deadlock 이력과 관련 SQL
- 세션 종료 요청과 승인 상태

### 인터랙션

- 그래프 구간 드래그로 인시던트 시간 범위 생성
- 지표 클릭 시 원인 쿼리 목록으로 이동
- 쿼리 클릭 시 프로시저 작업실로 이동

- 현재 상태를 인시던트에 첨부
- AI에게 선택 구간의 변화 설명 요청

### AI 인시던트 요약 형식

```text
현상: 주문 조회 API P95가 620ms에서 4.2초로 증가
```

## 6.12 AI DBA 챗봇

### 대표 질문

- “오늘 느려진 프로시저를 업무 영향 순으로 보여줘.”
- “이 프로시저가 어제보다 느려진 이유가 뭐야?”
- “현재 Lock의 최초 원인 세션을 찾아줘.”
- “이 SQL의 결과는 유지하면서 개선안을 만들어줘.”
- “지난 6개월간 사용 흔적이 없는 객체를 찾아줘.”
- “수정하면 영향받는 화면과 배치를 알려줘.”
- “테스트 DB에서 검증하고 승인 요청을 만들어줘.”

### 챗봇 작업 단계

1. 사용자의 의도를 구조화한다.
2. 대상 서버·DB·환경과 시간 범위를 명확히 고정한다.
3. 필요한 읽기 작업과 데이터 출처를 보여준다.
4. 분석 결과, 근거, 불확실성을 제시한다.
5. 변경이 필요하면 작업 계획과 diff를 생성한다.
6. 테스트와 영향 분석을 수행한다.
7. 승인 요청을 생성한다.
8. 승인된 도구만 호출한다.
9. 실행 결과와 사후 지표를 보고한다.

### 응답 표준

- 결론
- 영향 범위
- 측정 근거
- 원인 후보와 우선순위
- 권장 조치
- 예상 효과
- 위험과 부작용
- 신뢰도
- 다음 승인 단계

### 챗봇 안전 정책

- 자연어 입력을 SQL로 직접 연결하지 않는다.
- 모든 실행은 허용된 도구와 명령 유형을 통해서만 수행한다.
- 생성 SQL을 파싱해 명령 종류와 대상 객체를 확인한다.
- 운영 환경, 대상 DB, 대상 객체를 승인 화면에 재표시한다.
- DB 코드와 주석 속 문장을 시스템 지시로 해석하지 않는다.
- 대화 중 환경이 변경되면 기존 승인을 무효화한다.
- 승인된 SQL과 실제 실행 SQL의 해시가 다르면 차단한다.

- 상세 정보는 알림 본문 대신 콘솔 링크(인증 필요)로 연결한다.

## 7.1 기준선과 이상 탐지

- CPU, I/O, wait, lock 기여도

- 데이터 증가와 통계 변경

### 경보 예시

```text
usp_GetOrderSummary의 P95 실행시간이
```

## 8. 변경 실행 안전 체계

### 8.1 위험도 분류

| 위험도 | 예시 | 기본 승인 |
|---|---|---|
| 낮음 | 주석·포맷, 읽기 전용 분석 | 승인 불필요 또는 1인 |
| 보통 | 프로시저 수정, 제한적 인덱스 생성 | DBA 1인 |
| 높음 | 프로시저 삭제, 테이블 변경, 세션 종료 | DBA + 서비스 책임자 |
| 매우 높음 | 대량 데이터 수정, 광범위 DDL, 장기 Lock 예상 | 2인 승인 + 유지보수 시간 |
| 금지 | DB 삭제, 백업 없는 파괴 작업, 정책 외 명령 | 실행 차단 |

### 8.2 실행 전 검사

- 승인 대상과 실행 대상 일치
- 현재 객체 버전이 승인 시점과 동일
- 백업·복원 스크립트 존재
- 필요한 권한과 계정 유효시간 확인
- 현재 Lock, 부하, 복제 지연 확인
- 유지보수 시간과 금지 시간 확인
- 예상 실행시간과 타임아웃
- SQL 파싱과 금지 명령 확인

### 8.3 실행 중 보호

- 명령별 타임아웃
- Lock timeout
- 최대 영향 행 수 제한
- 트랜잭션과 savepoint 적용 가능 여부
- 단계별 진행·중단 상태 기록
- 승인되지 않은 후속 SQL 차단
- 연결 끊김과 부분 성공 처리

### 8.4 실행 후 검증

- 컴파일·객체 상태 확인
- 대표 입력 결과 동일성
- 오류율·실행시간·CPU·I/O 비교
- Lock·Deadlock 변화
- 호출 애플리케이션 오류
- 일정 관찰 기간 후 자동 결과 보고
- 악화 기준 충족 시 롤백 제안 또는 승인된 자동 롤백

### 9.1 고객망 에이전트

- 고객 DB에 가까운 네트워크에서 실행
- 중앙에서 DB로 직접 인바운드 연결하지 않는 구성을 우선
- 수집 주기, 동시 쿼리 수, 타임아웃과 부하 상한 적용
- 장애 시 로컬 버퍼링 후 재전송
- 수집 쿼리 서명과 버전 관리
- 중앙에서 임의 SQL을 내려보내지 않고 허용된 작업 정의를 사용
- 실행 계정 자격 증명은 중앙 AI가 직접 열람하지 못하게 한다.
- 에이전트 설치 파일과 업데이트는 코드 서명을 검증한 뒤에만 적용한다.
- 업데이트 채널은 TLS + 서명의 이중 검증을 사용하고, 버전 롤백 공격을 차단한다.
- 에이전트의 실행 무결성(변조 여부)을 주기적으로 중앙에 보고한다.

### 9.2 저장 데이터

- 운영 데이터 복제가 필요한 결과 동일성 검증은 별도 승인 항목으로 분리하고, 복제 범위(테이블·행 수·기간)를 승인 화면에 명시한다.
- 테스트 DB에도 운영과 동일한 접근 통제·감사 로그를 적용한다.
- 테스트 DB는 검증 완료 후 자동 파기하며, 파기 결과를 감사 로그에 남긴다.

## 11. 비기능 요구사항

### 11.1 수집 부하

- 정상 운영에서 수집으로 인한 평균 DB CPU 증가 목표: 1% 이내
- 고객이 수집 주기와 최대 부하를 설정 가능
- DB 부하가 임계치를 넘으면 비필수 수집 자동 완화
- 비효율적인 수집 쿼리를 자동 중단하고 보고

### 11.2 가용성

- 콘솔 장애가 고객 DB 운영에 영향을 주지 않아야 한다.
- 중앙 서비스 중단 중에도 에이전트는 DB 변경을 새로 수행하지 않는다.
- 실행 중 중앙 연결이 끊기면 사전 정의된 안전 정책에 따라 중단 또는 완료한다.

### 11.3 성능

- 홈 대시보드 주요 상태 3초 이내 표시 목표
- 실시간 지표 지연 기본 15~60초
- 객체 검색 2초 이내 목표
- 일반 AI 진단 첫 응답 10초 이내, 장기 분석은 진행 상태 표시

### 11.4 확장성

- 조직·서버 그룹 단위 수평 확장
- DB별 수집 주기와 보존 정책 분리
- 시계열과 객체 스냅샷 저장소 분리

### 11.5 접근성 및 사용성

- 색상만으로 상태를 구분하지 않는다.
- 키보드 탐색과 명확한 포커스 표시
- 전문 용어에는 쉬운 설명 제공
- 숫자와 시간 단위의 일관성
- 운영 환경 표시를 화면 이동 중에도 유지

## 12. UX 및 시각 설계 원칙

### 12.1 화면 계층

- 1단계: 정상·주의·위험과 업무 영향
- 2단계: 문제의 근거와 관련 객체
- 3단계: 원시 지표, 실행 계획, 세션과 SQL 전문 정보

### 12.2 정보 밀도

- 모니터링은 넓은 화면과 비교 그래프 중심
- 작업실은 코드와 분석 중심
- 승인 센터는 diff, 테스트, 위험과 롤백 중심
- 챗봇은 보조 패널로 제공하되 핵심 근거를 가리지 않는다.

### 12.3 환경 표시

- 운영: 붉은 계열 배지와 고정 문구
- 스테이징: 주황 계열
- 테스트: 파랑 계열
- 개발: 중립 또는 초록 계열
- 색상 외에도 환경명을 항상 텍스트로 표시한다.

### 12.4 알림 표현

- “CPU 90%”보다 “주문 조회 지연에 영향을 주는 CPU 포화”처럼 영향과 연결한다.
- 기술적인 wait type은 원문과 쉬운 설명을 함께 표시한다.
- 조치 버튼에는 수행 내용과 승인 필요 여부를 명시한다.

## 15. 기능별 완료 기준

### 15.1 모니터링

- 사용자가 30초 이내에 가장 위험한 DB와 원인을 찾을 수 있다.
- 경보의 근거 시간 범위와 기준선을 확인할 수 있다.
- 그래프에서 관련 쿼리·프로시저·세션으로 이동할 수 있다.
- 수집 공백과 데이터 신선도가 표시된다.

### 15.2 AI 진단

- 모든 결론에 데이터 출처와 관찰 기간이 표시된다.
- 추정과 확인된 사실을 구분한다.
- 신뢰도가 낮으면 추가 확인 방법을 제시한다.
- 존재하지 않는 객체나 지표를 근거로 사용하지 않는다.

### 15.3 프로시저 수정

- 변경 전후 diff를 확인할 수 있다.
- 입력·출력 호환성과 결과 비교가 제공된다.
- 실행 계획과 핵심 성능 지표가 비교된다.
- 승인한 SQL과 실행한 SQL이 동일함을 검증한다.
- 이전 버전으로 복원할 수 있다.

### 15.4 프로시저 삭제

- 의존성과 최근 관찰 이력을 확인하지 않으면 승인할 수 없다.
- 원본 DDL과 권한이 백업된다.
- 운영 삭제는 고위험 정책을 적용한다.
- 삭제 후 호출 오류와 복원 상태를 관찰한다.

### 15.5 보안

- 비밀 값이 로그와 UI에 노출되지 않는다.
- 읽기 계정만으로 운영 변경을 수행할 수 없다.
- 모든 운영 변경은 승인과 감사 기록을 남긴다.
- DB 콘텐츠의 악성 지시가 AI 도구 호출로 이어지지 않는다.


## 23. 최종 정리

DBA ONE의 핵심 경쟁력은 AI가 SQL을 작성하는 기능 자체가 아니다. 다음 조건을 함께 충족하는 것이 제품의 본질이다.

- 데이터베이스를 지속적으로 관찰한다.
- 이상을 업무 영향과 연결해 설명한다.
- 실제 측정값으로 원인을 증명한다.
- 변경 결과와 위험을 사전에 검증한다.
- 권한 있는 사용자가 이해하고 승인할 수 있게 한다.
- 승인된 작업만 안전하게 실행한다.
- 적용 후 정상화와 롤백 가능성까지 책임진다.

따라서 제품 메시지는 다음으로 확정한다.

> **DBA ONE — 데이터베이스를 24시간 관찰하고, 문제를 진단하며, 검증된 개선안을 승인 아래 안전하게 실행하는 AI DBA 플랫폼**
