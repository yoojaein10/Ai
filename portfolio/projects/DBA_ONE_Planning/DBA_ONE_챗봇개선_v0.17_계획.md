## 1. 로컬 스키마 검색 — 한글 하이브리드 검색 (SQLite FTS5)

현재 테이블 최대 1,500개를 Gemini에 보내 고르게 하는 구조를, 로컬 검색으로 관련 테이블 5~10개만 추려 전달하는 구조로 바꾼다. **가장 투자 대비 효과가 큰 항목.**

### 검색 대상
- 스키마·테이블·컬럼명 (영문 객체명)
- MS_Description
- 용어집 (knowledge.json)
- 과거 정답 사례 (정규화 저장 — §3 참조)
- 객체 의존성

### 토크나이저 전략 — 순수 trigram 금지, 하이브리드로
FTS5 trigram은 3글자 미만 질의에 MATCH되지 않으므로 "접수·건수·주문" 같은 2글자 핵심어가 많은 한국어 DBA 질문에 단독 사용 부적합. unicode61은 "접수건수" vs "접수 건수" 토큰 분리 문제가 있음. 따라서:

- **정규화된 이름·동의어 필드**: unicode61
- **3글자 이상 부분 문자열 검색**: trigram (색인 대상은 이름·설명 필드로 한정 — trigram 인덱스는 크기가 원문 대비 수 배로 커짐)
- **1~2글자 용어**: 용어집 동의어와 정확·접두 검색
- 영문 객체명, 한글 띄어쓰기 제거형을 별도 검색 필드에 저장
- 런타임에서 trigram 지원 여부를 실제 테이블 생성으로 확인 (SQLite 3.34+ 필요)
- **조합·가중치는 평가셋의 Recall@5/10으로 결정** — "trigram 채택"이 아니라 "하이브리드 검색을 평가 후 확정"

### 검색 실패 fallback
- 최고 점수가 임계치 미만이면 후보를 20~30개로 확대하거나 사용자 재질문으로 전환
- 후보 테이블 간 점수 차가 작을 때도 재질문 트리거 (§6)

### FTS 질의 생성 — '이스케이프'가 아니라 안전한 쿼리 생성
`MATCH ?` 바인딩은 SQL 주입만 막고 FTS5 자체 문법(NEAR, NOT, `*`, `-`, `col:` 필터, 따옴표)은 그대로 해석된다. 사용자 질문을 그대로 MATCH에 넣지 않는다:

1. 애플리케이션이 질문을 토큰화
2. 빈 토큰·제어문자·연산자 전용 토큰 제거
3. 각 토큰을 큰따옴표 구문으로 감싸고 내부 `"`는 `""`로 치환
4. 애플리케이션이 명시적으로 AND 또는 OR 조합
5. 최종 생성 문자열만 `MATCH ?`에 바인딩

회귀 테스트: 따옴표·괄호·NEAR·AND/OR/NOT·`col:`·매우 긴 입력.

## 2. 라우팅 통합 — 단일 Gemini JSON 호출

- 로컬 규칙 분류(프롬프트 구성 힌트 용도): 건수·합계·목록·기간→데이터 / 생성·수정·크기·객체→메타데이터 / 프로시저명+느림·분석→프로시저 / 상태·블로킹·성능→일반 상담
- 별도 라우터 호출을 두지 않고, **단일 Gemini 호출의 JSON 응답에 `route` 필드를 포함** — 테이블 선택·SQL 생성·라우팅을 한 번에
- 오분류 사례는 로그로 수집해 규칙을 주기적으로 개선

## 3. FTS DB·과거 사례 — 민감한 파생 데이터로 취급

FTS5 일반 테이블은 색인 원문 사본을 shadow 테이블에 보관하고, 삭제 항목도 병합 전까지 복구 가능성이 있다. contentless여도 암호화가 아니다.

- SQL뿐 아니라 설명·용어집도 **저장 전 정제**
- 과거 사례는 원문 SQL 대신 **정규화 SQL 구조 + 사용 객체·컬럼 + 의도**만 저장 (리터럴은 검색 노이즈이기도 함)
- FTS DB와 백업 모두 ACL 제한 (v0.16의 config.json ACL 방식과 동일: 사용자+SYSTEM)
- 보존기간·삭제·재색인 정책 명시, secure-delete 옵션 검토
- **실제 Gemini 전송 직전에도 별도 정제** (이중 방어)

## 4. 스키마 캐시 — 권한 지문 포함

- target_id별 객체·컬럼·설명 캐시, 객체 변경 감지 시 해당 캐시만 무효화
- **권한 변경은 modify_date로 잡히지 않음** → 캐시 키/무효화 조건에 권한 지문 포함:
  - target_id
  - 사용자·역할 토큰 (**sys.database_role_members 역할 멤버십 포함**)
  - 관련 sys.database_permissions
  - 스키마 버전
- 연결·대상 전환 시 지문 재계산
- **검색 결과도 현재 사용자가 접근 가능한 객체로 재필터링** — 캐시가 권한 경계를 우회하는 통로가 되지 않도록
- Query Store·서버 상태는 30~60초 캐시
- 동일 질문 + 동일 스키마 버전이면 검색 결과 재사용

## 5. 대화 문맥 압축 — 마스킹 전제

모델에 보내는 것:
- 최근 4턴
- 현재 대상 객체·기간·필터
- 확정된 사용자 의도
- **mask_sql()을 거친 실행 SQL** (사용자가 수정한 리터럴 포함 가능성 때문에 원문 전송 금지) + 참조 테이블·컬럼 + SQL 구조 + 실행 성공 여부 + 결과 행 수
- 중요한 교정 사항 요약

규칙:
- **결과 데이터 행은 절대 외부 LLM에 전송하지 않음** (행 수·컬럼 목록까지만)
- 사용자 교정 사항은 4턴이 지나도 세션 종료까지 유지하되, **자유문장이 아닌 구조화된 사실로만 저장** (지속형 프롬프트 인젝션 방지). 스키마를 사전 정의: ① 용어→객체 매핑 ② 기본 기간 필터 ③ 제외 조건 — 이 3유형으로 제한
- 전송 전 MS_Description·용어집에 시크릿/내부 URL/계정명 포함 여부 점검

## 6. 모호한 질문은 추측하지 않기

- 확신이 낮으면 SQL 생성 대신 선택지 제시
  - 예: "'접수 건수'가 주문 접수인지 고객 문의 접수인지 확인이 필요합니다."
- 트리거: 검색 최고 점수 낮음, 후보 간 점수 차 작음, route 확신 낮음
- 환각 SQL 1회의 신뢰 비용 > 재질문 1회의 비용 — 환각 감소에 모델 업그레이드보다 효과적일 수 있음

## 7. 단계별 계측

각 AI 호출에 기록:
- route_ms, schema_search_ms, generation_ms, total_ms
- 입력·출력 토큰, 선택 테이블 수, 성공·검증 실패 여부

로그 위생:
- 질문 원문 대신 **설치별 비밀키 HMAC** + 분류 정보만 기록 (흔한 질문은 일반 해시로 추측 가능)
  - **HMAC 키는 DPAPI로 보호** — 키가 로그와 같은 위치에 평문으로 있으면 무의미
- 결과 데이터는 로그에 기록하지 않음
- 로그 보존기간 설정

## 8. 정확도 평가 세트 (30~50개) — v0.16 기준선 먼저

유형: 단순 건수·합계 / 기간별 집계 / 조인 필요 / 모호(재질문 유도) / 존재하지 않는 테이블 / 프로시저 성능·변경 / 후속 질문

지표:
- 경로 분류 정확도, 올바른 테이블 선택률, SQL 구문 성공률, 결과 정답률
- 허구 객체·컬럼 생성률, 재질문 적절성
- **Recall@5, Recall@10, MRR(정답 테이블 순위)**
- **후보군에 정답 테이블이 없었던 비율**
- **검색 실패 / 생성 실패 / 검증 차단 분리 집계**
- 응답시간 p50/p95, 질문당 호출 수·토큰
- **v0.16 기준선 대비 v0.17 비교** — 개선 전 baseline 없이 리팩터링 금지

보안:
- 평가 질문·기대 결과에 실데이터/PII 미포함 (합성 또는 마스킹)
- 평가는 최소권한 읽기전용 계정(dbaone_reader) + 대상 DB allowlist 안에서만
