# 연봉 관리 — USB 암호화 저장 설계 문서

- **작성일**: 2026-08-19
- **브랜치**: `feature/salary-usb-vault` (main 기준)
- **상태**: 설계 승인 완료 → 구현 계획 전환 예정
- **포지셔닝**: 연봉 데이터는 **서버 DB에 저장하지 않는다.** 인사담당자 PC에 연결된 USB의 단일 암호화 파일이 유일한 저장소이며, 서버는 "누가 언제 열었는가"만 안다.

## 1. 결정사항 요약

| # | 항목 | 결정 |
|---|---|---|
| 1 | 저장 위치 | 인사담당자 PC의 USB. 브라우저 File System Access API로 직접 읽기/쓰기. **서버는 연봉 데이터를 모름** |
| 2 | 데이터 범위 | 직원별 **연도별 연봉 이력** (연도 / 적용일 / 연봉액 / 인상률 / 비고) |
| 3 | 키 관리 | 사용자 비밀번호 → PBKDF2-SHA256 유도. **복구키·백도어 없음** |
| 4 | 감사 로그 | 접근 기록만 서버 DB. 금액·직원명은 서버로 전송하지 않음 |
| 5 | 저장 방식 | **명시적 [저장] 버튼**. 편집은 메모리에만 누적, dirty 상태 이탈 시 경고 |
| 6 | 자동 잠금 | **10분** 무입력 시 키·평문 폐기. 30초 전 경고 |
| 7 | 암호화 | AES-256-GCM, PBKDF2-SHA256 210,000회, **IV는 저장마다 새 난수** |
| 8 | 백업 | 저장 시 `salary.enc.bak` 1세대 유지. 원본 덮어쓰기보다 먼저 수행 |
| 9 | 브라우저 | Chrome / Edge 전용 (Firefox·Safari 미지원) |
| 10 | 권한 | 메뉴·라우트는 `SYSTEM_ADMIN` / `HR_ADMIN`. 단 실질 방어는 파일 비밀번호 |
| 11 | UI | 단일 페이지 `/salary`, 4개 상태 (미연결 / 잠김 / 열림 / 오류) |
| 12 | 담당자 위임 | 2단계 — 전임자가 후임자·현재 비번 입력 → **후임자가 직접 새 비번 입력**. 새 salt로 전체 재암호화 후 즉시 잠금 |
| 13 | 위임 시 서버 역할 | **자동 이전하지 않음.** 파일 비밀번호만 넘긴다. 역할 부여는 관리자 화면에서 수작업 (§9.1) |
| 14 | IP 접근 제한 | 담당자 PC의 **고정 IP 1개**만 허용. 불일치 시 서버가 잠금 해제를 거부하고 `IP_DENIED`를 기록 |
| 15 | 제한 강도 | **소프트** — 서버가 거부할 뿐 복호 자체를 막지는 못한다. 우회 가능함을 전제로 한다 (§9.2) |

## 2. 위협 모델과 보안 경계

이 기능의 목적은 서버 침해로부터 연봉을 보호하는 것이다. 무엇을 막고 무엇을 못 막는지 명확히 한다.

### 2.1 막는 것

| 위협 | 차단 근거 |
|---|---|
| 서버 DB 유출 | 연봉 데이터가 DB에 **존재하지 않음** |
| 서버 관리자의 무단 열람 | 서버에 평문·암호문 모두 없음 |
| 네트워크 도청 | 연봉 데이터가 네트워크를 흐르지 않음 |
| USB 분실·도난 | AES-256-GCM 암호문. 비밀번호 없이 복호 불가 |
| 파일 변조 | GCM 인증 태그 + 헤더를 AAD로 바인딩 |
| 자리 비움 중 화면 노출 | 10분 자동 잠금 |
| 다른 자리·재택에서의 무심코 열람 | 허용 IP 1개 제한 (§9.2). 비기술적 사용자 한정 |
| 담당자 교체 후 전임자의 계속 접근 | 위임 시 후임자가 정한 새 비밀번호로 전체 재암호화 (§8.1.2) |

### 2.2 막지 못하는 것 (설계상 한계 — 운영 규칙으로 보완)

| 한계 | 이유 |
|---|---|
| 인사담당자 PC 자체의 침해 | 키가 메모리에 있는 동안 브라우저·OS를 장악하면 평문 접근 가능 |
| 실제로 USB에 저장했는지 강제 | 브라우저는 저장 매체 종류를 알 수 없다 |
| INSA 밖에서의 파일 접근 | 비밀번호를 아는 사람은 별도 도구로 복호 가능 |
| 감사 로그 우회 | 위와 같은 이유로 서버 로그가 완전성을 보증하지 못함 |
| 비밀번호 분실 | 복구 수단이 없다. **영구 소실** |
| 위임 전에 전임자가 파일을 복사해 둔 경우 | 위임은 **앞으로의 접근만** 끊는다. 복사본은 옛 비밀번호로 계속 열린다. 위임 시점 이전의 데이터 유출은 어떤 재암호화로도 되돌릴 수 없다 |
| 허용 IP 밖에서의 접근 (기술적 우회) | IP 제한은 **소프트**다. 서버 응답을 무시하면 복호는 그대로 일어난다. 비기술적 사용자에게만 유효하다 (§9.2.1) |

### 2.3 보안 경계의 유일한 통제점

**비밀번호 관리가 이 기능의 전부다.** 프론트엔드 역할 가드는 메뉴를 숨기는 UX 장치이며 방어력이 없다. 역할 가드를 우회해 `/salary`에 직접 진입해도 비밀번호가 없으면 잠금 화면만 보인다.

## 4. 파일 포맷 명세

파일명 `salary.enc`, 백업 `salary.enc.bak`.

### 4.1 바이너리 레이아웃

| offset | size | 필드 | 값 |
|---|---|---|---|
| 0 | 8 | `magic` | ASCII `"INSASAL1"` |
| 8 | 1 | `version` | `0x01` |
| 9 | 4 | `kdfIter` | uint32 big-endian (기본 210000) |
| 13 | 16 | `salt` | 난수. **파일 생성 시 1회 고정** |
| 29 | 12 | `iv` | 난수. **저장할 때마다 새로 생성** |
| 41 | n | `ciphertext` | AES-256-GCM 암호문 + 16바이트 인증 태그 |

헤더 총 41바이트.

### 4.2 AAD 바인딩

GCM의 AAD(추가 인증 데이터)로 **헤더 41바이트 전체**를 사용한다. 공격자가 `kdfIter`·`salt`·`iv`를 바꾸면 태그 검증이 실패한다.

> 이 항목은 설계 1부에 없던 추가분이다. 사용자 결정을 바꾸지 않는 순수 강화이므로 스펙 리뷰에서 제외해도 무방하다.

### 4.3 평문 JSON

```json
{
  "schemaVersion": 1,
  "updatedAt": "2026-08-19T01:23:45.000Z",
  "records": [
    {
      "empId": 123,
      "empNo": "20180012",
      "empName": "홍길동",
      "year": 2026,
      "effectiveDate": "2026-01-01",
      "annualSalary": 52000000,
      "raiseRate": 4.5,
      "note": "승진 반영"
    }
  ]
}
```

- 레코드 식별자는 **`(empId, year)` 조합**. 같은 직원의 같은 연도 레코드는 하나만 존재한다.
- `empNo`·`empName`은 **스냅샷**이다. 파일만으로 판독 가능해야 하고, 퇴사자가 DB에서 사라져도 이력이 남아야 하기 때문이다.
- 표시용 부서·직급은 파일에 넣지 않는다. `/api/v1/employees`에서 조회해 `empId`로 조인한다.
- `annualSalary`는 정수(원), `raiseRate`는 소수 1자리 퍼센트. 둘 다 계산하지 않고 입력값 그대로 보관한다.

## 5. 암호화 명세

| 항목 | 값 |
|---|---|
| KDF | PBKDF2-SHA256, 210,000회, salt 16B → 256bit 키 |
| 암호 | AES-256-GCM, IV 12B, 태그 128bit |
| AAD | 헤더 41바이트 |
| 구현 | Web Crypto (`crypto.subtle`). 외부 암호 라이브러리 의존 없음 |

### 규칙

1. **IV 재사용 금지.** 저장할 때마다 `crypto.getRandomValues(new Uint8Array(12))`로 새로 만든다. GCM에서 같은 키에 같은 IV를 두 번 쓰면 평문이 복원될 수 있다. 이 규칙은 단위 테스트로 강제한다(§12.1).
2. **salt는 파일 생성 시 1회 고정.** 저장마다 바꾸면 매번 PBKDF2 210,000회를 다시 돌려야 한다.
3. **파생 키는 `CryptoKey` 객체로만 보관**하고 `extractable: false`로 만든다. 원시 키 바이트를 JS 변수에 두지 않는다.
4. **비밀번호 문자열은 키 유도 직후 참조를 끊는다.** JS에서 문자열 메모리를 지울 수는 없으나 참조는 남기지 않는다.

> **수용된 편차 (2026-08-19, 최초 구현 시점):** 이 규칙은 **아직 지켜지지 않는다.**
> `useSalaryVault`가 평문 비밀번호를 `passwordRef`에 담아 잠금 해제부터 잠금까지 세션 내내 유지한다
> (`save`와 `reencrypt`가 재암호화에 그 값을 쓰기 때문). ref는 React DevTools의 hooks 인스펙터에 그대로 보인다.
>
> **위험:** 공격 전제는 "잠금 해제된 무인 세션"으로 화면 열람과 같지만, 결과가 다르다 —
> 화면 열람은 그 순간에 그치는 반면, 비밀번호를 얻으면 **USB나 그 사본을 어디서든 영구히 복호**할 수 있다.
> §2.2의 "PC 침해" 한계가 이 상승분까지 인정하는 것은 아니다.
>
> **해소 방법:** `passwordRef` 대신 파생된 `CryptoKey`(이미 `extractable: false`)와 파일의 salt를 보관한다.
> `save`는 새 비밀번호가 필요 없고 `reencrypt`는 인자로 받으므로, `crypto.ts`에 키를 받는 변형
> (`encryptVaultWithKey` 등)을 추가하면 된다. 약 20줄.
>
> **연기 사유:** 최종 수정 웨이브에서 위임 후 `.bak`이 옛 비밀번호로 열리던 Critical을 닫는 것이 우선이었고,
> 같은 웨이브에서 `crypto.ts`(브랜치에서 가장 민감한 모듈)를 함께 건드리면 그 수정의 위험이 커진다고 판단했다.
> 별도 후속 작업으로 처리한다.
5. `kdfIter`는 파일에서 읽어 쓰되 **하한 100,000을 강제**한다. 그 미만이면 파일을 거부한다.

## 6. 모듈 구성

### 6.1 `frontend/src/salary/crypto.ts` — 순수 함수

```
encryptVault(plain: VaultData, password: string, salt?: Uint8Array): Promise<Uint8Array>
decryptVault(bytes: Uint8Array, password: string): Promise<VaultData>
parseHeader(bytes: Uint8Array): VaultHeader        // magic·version·kdfIter 검증
```

파일시스템·React·네트워크를 import하지 않는다.

### 6.2 `frontend/src/salary/vault.ts` — 파일 입출력

```
isFileSystemAccessSupported(): boolean
pickVaultDirectory(): Promise<FileSystemDirectoryHandle>   // showDirectoryPicker
saveHandle(dir) / loadHandle(): IndexedDB 보관·복원
verifyPermission(dir, mode): Promise<boolean>              // 재접속 시 1클릭 재승인
vaultExists(dir): Promise<boolean>                         // salary.enc 유무
readVault(dir): Promise<{ bytes, lastModified }>
writeVault(dir, bytes): Promise<void>                      // .bak 먼저, 그다음 원본
```

암호를 모른다. 바이트만 다룬다.

**파일이 아니라 폴더를 선택받는 이유**: `FileSystemFileHandle` 하나로는 같은 폴더에 형제 파일을 만들 수 없다. `salary.enc.bak`을 쓰려면 부모 폴더 핸들이 필요하므로 `showDirectoryPicker()`로 **USB 폴더**를 받는다. 파일명은 `salary.enc`로 고정한다. 부수 효과로 "새 금고 만들기"도 같은 폴더에서 자연스럽게 처리된다.

**`.bak`의 내용은 "저장 직전의 원본"이다.** `writeVault`는 ① 현재 `salary.enc`를 읽어 그대로 `salary.enc.bak`에 쓰고, ② 그다음에 새 바이트로 `salary.enc`를 덮어쓴다. 따라서 ② 도중 USB가 분리되어도 `.bak`에는 **직전까지의 정상 데이터**가 남는다. 새 내용을 `.bak`에 쓰는 것이 아니다.

### 6.3 `frontend/src/salary/useSalaryVault.ts` — 상태 훅

상태 기계(§7), dirty 추적, 10분 자동 잠금 타이머, `beforeunload` 가드, 감사 로그 전송 트리거를 담당한다.

## 7. 화면 상태 기계

```
[① 미연결]  폴더 핸들 없음
   └─ "USB 폴더 선택" → showDirectoryPicker
        ├─ 폴더에 salary.enc 있음 → ②
        └─ 없음 → "새 연봉 금고 만들기" 비밀번호 2회 입력 → 빈 파일 생성 → ③

[② 잠김]   폴더 핸들 있음(IndexedDB 복원), 키 없음
   ├─ 권한 재승인 1클릭 + 비밀번호 입력 → 복호화 성공 → ③
   └─ 복호화 실패 → 오류 표시, ② 유지 (5회 연속 실패 시 60초 대기)

[③ 열림]   평문이 메모리에만 존재
   ├─ 조회 / 등록 / 수정 / 삭제 → dirty = true
   ├─ [저장] → 재암호화(새 IV) → .bak → salary.enc → dirty = false
   └─ [잠그기] · 10분 자동잠금 · 탭 종료 → 키·평문 폐기 → ②

[④ 오류]   magic 불일치 / 미지원 버전 / 외부 변경 감지
   └─ 읽기 전용 안내 + .bak 복원 제안. 자동 덮어쓰기 금지
```

### 전환 규칙

- ③ → ② 전환 시 `CryptoKey` 참조와 평문 `records` 배열을 모두 버린다. dirty 상태였다면 **먼저 저장 여부를 묻는다**.
- 자동 잠금 타이머는 키 입력·마우스 이동·스크롤에서 리셋한다. 잠기기 30초 전 카운트다운을 띄운다.
- ①·②·④ 상태에서는 Toolbar와 테이블을 **렌더링하지 않는다**. DOM에 금액이 존재하면 안 된다.

## 8. 화면 레이아웃

INSA 표준 페이지 문법을 그대로 따른다. 경로는 `/salary`, GNB "인사" 하위.

| 영역 | 내용 |
|---|---|
| **Header** | "연봉 관리" + 상태 뱃지(`열림` / `잠김`) + `[비밀번호 변경]` + `[담당자 위임]` + `[잠그기]` + `[저장]`(dirty면 Primary 활성) |
| **Toolbar** (sticky) | 연도 Select · 부서 Select · 직원 검색 · `[+ 연봉 등록]` |
| **Primary** | 테이블: 직원명 / 사번 / 부서 / 연도 / 적용일 / **연봉액** / 인상률 / 비고 |
| **Context Panel** | 선택 직원의 연도별 이력 타임라인 (인상률 추이) |

- AntD `size="small"`, row 32px. 금액은 `tabular-nums` 우측 정렬, 천단위 구분.
- 빈 상태(① 미연결)는 Gowun Dodum 디스플레이 + 앰버 액센트를 허용한다.
- 삭제는 저채도 + 타이핑 확인 (Quiet Destructive 원칙).
- Primary 버튼은 화면당 1개 — dirty일 때는 `[저장]`이, 그 외에는 `[+ 연봉 등록]`이 Primary.

### 8.1 비밀번호 변경 · 담당자 위임

둘 다 상태 ③에서만 가능하며, 암호학적으로는 같은 동작(**새 salt로 전체 재암호화**)이다. `encryptVault(plain, newPassword)`를 salt 인자 없이 호출하면 salt가 새로 생성되므로(§6.1) 별도 암호 함수가 필요 없다. 차이는 **누가 새 비밀번호를 입력하는가**와 **감사 기록에 후임자가 남는가**이다.

| | 비밀번호 변경 | 담당자 위임 |
|---|---|---|
| 상황 | 같은 담당자가 계속 맡음 | 인사 담당자 교체 (약 2년 주기) |
| 새 비밀번호 입력자 | 본인 | **후임자 본인** |
| 감사 action | `PASSWORD_CHANGE` | `DELEGATE` (+ `target_user_id`) |
| 완료 후 | 상태 ③ 유지 | **즉시 잠금 → 상태 ②** |

#### 8.1.1 위임이 2단계인 이유

전임자가 새 비밀번호를 입력하면 전임자가 그 비밀번호를 알게 된다. 서버 역할을 회수해도 **USB만 있으면 INSA 없이 파일을 복호할 수 있으므로** 위임이 성립하지 않는다. 따라서 새 비밀번호는 후임자만 입력한다.

#### 8.1.2 위임 흐름

```
[1단계 — 전임자가 조작]
  후임자 선택 (활성 사용자 목록)
  현재 비밀번호 입력
    └─ 검증: 현재 비밀번호로 복호에 성공해야만 다음 단계로 간다
  [다음] → "이제 후임자에게 자리를 넘겨주세요" 전체 화면 안내

[2단계 — 후임자가 조작]
  헤드라인: "○○○ 님, 새 비밀번호를 입력하세요.
             전임자에게 보이지 않습니다."
  새 비밀번호 2회 입력 (마스킹)
  [위임 완료]
    ├─ 새 salt + 새 IV로 전체 재암호화
    ├─ .bak → salary.enc 저장 (§6.2)
    ├─ 감사로그 DELEGATE 전송 (target_user_id = 후임자)
    └─ 즉시 잠금 → 상태 ②
```

**완료 직후 잠그는 이유는 두 가지다.** 화면이 열린 채 남으면 전임자가 되돌아와 볼 수 있고, 후임자가 방금 정한 비밀번호로 실제로 열리는지 **그 자리에서 확인**해야 하기 때문이다.

#### 8.1.3 규칙

- **dirty 상태에서는 위임을 시작할 수 없다.** 먼저 저장하도록 요구한다. 재암호화가 저장을 겸하므로, 미저장 편집이 위임에 묻어 들어가면 무엇이 저장됐는지 불분명해진다.
- **위임 모달이 열려 있는 동안 10분 자동 잠금을 유예한다.** 후임자가 입력하는 도중 잠기면 안 된다. 대신 모달 자체에 5분 제한을 두고, 초과하면 취소하고 잠근다.
- **2단계에서 취소하면 파일은 전혀 바뀌지 않는다.** 1단계는 검증만 하고 아무것도 쓰지 않는다.
- 1단계에서 현재 비밀번호를 다시 묻는 것은, 담당자가 자리를 비운 사이 타인이 위임을 실행하는 것을 막기 위한 **재인증**이다. 이미 상태 ③이라 키는 메모리에 있다.
- 후임자에게 `HR_ADMIN`·`SYSTEM_ADMIN` 역할이 없으면 완료 화면에 **경고 배너**를 띄운다: "후임자에게 연봉 메뉴 권한이 없습니다. 관리자 화면에서 부여하세요." 역할을 자동으로 바꾸지는 않는다(§9.1).

## 9. 권한

| 겹 | 구현 | 실제 방어력 |
|---|---|---|
| 메뉴 노출 | `menuRegistry.ts` → `roles: ["SYSTEM_ADMIN","HR_ADMIN"]` | 없음 (UX) |
| 페이지 내 역할 체크 | `SalaryPage` · `SalaryAdminPage`가 `useAuthStore().roles`를 직접 확인 | 없음 (UX) |
| 파일 비밀번호 | PBKDF2 + AES-256-GCM | **전부** |
| 감사 로그 API | `require_roles(...)` (`backend/app/core/deps.py`) | 로그 위조 방지에 한함 |

서버가 연봉 데이터를 갖지 않으므로 **서버측 인가로 연봉을 보호할 방법은 원리적으로 없다.** 서버 인가가 실제로 걸리는 곳은 감사 로그 API뿐이다.

### 9.1 위임이 서버 역할을 건드리지 않는 이유

담당자 위임(§8.1)은 **파일 비밀번호만** 넘긴다. 후임자에게 `HR_ADMIN`을 부여하거나 전임자에게서 회수하지 않는다. 근거는 두 가지다.

1. **역할은 실제 통제점이 아니다.** 파일 비밀번호가 전부다(§2.3). 역할을 옮겨도 비밀번호를 아는 사람은 여전히 열 수 있고, 비밀번호를 모르는 사람은 역할이 있어도 못 연다.
2. **의존할 API가 안전하지 않다.** `backend/app/api/v1/admin.py`의 모든 엔드포인트가 `get_current_user`만 쓰고 `require_roles`를 **한 번도 걸지 않는다.** `PATCH /admin/users/{id}`에 `role_ids`를 주면 기존 역할을 전부 지우고 재부여한다(`services/admin.py:116-119`). 즉 현재는 일반 `EMPLOYEE`도 자신에게 `SYSTEM_ADMIN`을 붙일 수 있다.

> **이 API 가드 부재는 본 설계의 범위 밖이며 여기서 고치지 않는다.** 다만 위임 기능이 그 API에 의존하면 취약한 기반 위에 서게 되므로, 의존하지 않는 쪽을 택했다. 별도 이슈로 수정을 권고한다.

대신 위임 완료 화면에서 후임자의 역할을 조회해, 연봉 메뉴 권한이 없으면 경고 배너와 관리자 화면 링크를 띄운다.

### 9.2 IP 접근 제한

연봉 담당자 PC의 **고정 IP 1개**만 허용한다. 다른 자리에서는 잠금 해제를 거부한다.

#### 9.2.1 소프트 제한이라는 뜻

서버는 금고 파일을 갖고 있지 않다. 복호는 브라우저 안에서 로컬 파일로 일어난다. 따라서 **서버가 거부해도 그 응답을 무시하면 파일은 열린다.** 브라우저 개발자도구를 쓸 줄 아는 사람에게는 통하지 않는다.

그럼에도 값이 있는 이유는, 실제로 막고자 하는 것이 기술적 공격자가 아니라 **다른 자리에서 무심코 열어보는 상황**이기 때문이다. 인사팀 직원 수준에서는 확실히 막히고, 거부 시도가 `IP_DENIED`로 남아 사후 추적이 된다.

> 복호 자체를 막으려면 서버가 키의 일부(pepper)를 쥐고 IP 확인 후에만 내주는 방식이 필요하다. 서버 장애 시 연봉 파일을 열 수 없고 pepper 유실 시 영구 소실이라는 대가가 있어 **이번 범위에서 제외했다**(§14).

#### 9.2.2 신규 테이블 `insa_salary_vault_policy`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | INT PK IDENTITY | |
| `owner_user_id` | INT FK → `insa_user.id` UNIQUE | 연봉 담당자 |
| `allowed_ip` | VARCHAR(45) | 허용 IP 정확히 1개 |
| `is_active` | BIT DEFAULT 1 | |
| `updated_by` | INT FK → `insa_user.id` | 정책을 바꾼 사람 |
| `updated_at` | DATETIME | |

활성 행은 **1개만** 존재한다(담당자 1명 전제). 위임으로 담당자가 바뀌면 이 행을 갱신한다.

#### 9.2.3 검증 지점

`SalaryPage` 진입 시와 잠금 해제 직전에 `GET /api/v1/salary/policy/check`를 호출한다. 서버는 요청 IP를 정책과 대조해 `{ allowed, currentIp, reason }`을 돌려준다.

- `allowed: false`이면 비밀번호 입력란 자체를 렌더링하지 않고, 현재 IP와 함께 "이 자리에서는 연봉 금고를 열 수 없습니다"를 표시한다.
- 동시에 `IP_DENIED` 감사 로그를 남긴다. **거부된 시도야말로 반드시 기록해야 한다.**
- `currentIp`를 화면에 보여주는 이유는 담당자가 관리자에게 그대로 알려 정책을 고칠 수 있게 하기 위해서다. 자기 IP는 이미 자신이 알 수 있는 값이라 노출 위험이 없다.

#### 9.2.4 정책 미설정 시에는 허용한다

정책 행이 없으면 `allowed: true`를 돌려준다. 기본 거부로 하면 최초 설정 자체가 불가능해지기 때문이다. 대신 관리자 화면에 "허용 IP가 설정되지 않았습니다" 경고를 상시 표시한다.

#### 9.2.5 잠김 대비 (중요)

IP를 정확히 1개로 묶으면 **PC 교체·랜카드 교체·DHCP 갱신·VPN 접속만으로 담당자가 못 열게 된다.** 다음을 반드시 갖춘다.

- 정책 수정은 `SYSTEM_ADMIN`이 관리자 화면에서 언제든 할 수 있다.
- 관리자 화면에 **`[현재 접속 IP로 설정]` 버튼**을 둔다. 담당자 자리에서 관리자가 로그인해 한 번에 맞출 수 있다.
- 거부 화면에 현재 IP를 크게 표시해, 전화로 불러줄 수 있게 한다.
- **사내망이 DHCP라면 담당자 PC에 고정 IP를 할당해야 한다.** 이는 기술이 아니라 운영 전제다(§15).

#### 9.2.6 위임과의 관계

위임(§8.1.2)은 정책을 **자동으로 바꾸지 않는다.** 정책 변경은 `SYSTEM_ADMIN` 전용이고 위임은 `HR_ADMIN`도 수행하므로, 자동 변경은 권한 경계를 무너뜨린다. §9.1에서 역할 이전을 자동화하지 않기로 한 것과 같은 이유다.

대신 위임 완료 배너에 한 줄을 더한다: "후임자가 다른 자리를 쓴다면 관리자가 허용 IP를 갱신해야 합니다."

## 10. 감사 로그

### 10.1 신규 테이블 `insa_salary_access_log`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | INT PK IDENTITY | 프로젝트 전체가 `Integer` PK를 쓴다 |
| `user_id` | INT FK → `insa_user.id` | 행위자 |
| `action` | VARCHAR(20) | `OPEN` / `UNLOCK_FAIL` / `SAVE` / `CREATE_VAULT` / `LOCK` / `PASSWORD_CHANGE` / `DELEGATE` / `IP_DENIED` / `POLICY_CHANGE` |
| `target_user_id` | INT NULL FK → `insa_user.id` | `DELEGATE`일 때 **후임자**. 그 외에는 NULL |
| `record_count` | INT NULL | 열기·저장 시 레코드 건수 (**금액 아님**) |
| `ip_address` | VARCHAR(45) | IPv6 대응 |
| `user_agent` | VARCHAR(255) | |
| `occurred_at` | DATETIME NOT NULL | 서버 시각 |

인덱스: `(user_id, occurred_at DESC)`, `(occurred_at DESC)`.

### 10.2 스키마 차원의 금지 (다면평가 익명성과 동일한 방식)

다음 컬럼은 **존재하지 않는다.** 실수로도 저장될 수 없다.

`emp_id` · `emp_no` · `emp_name` · `annual_salary` · `raise_rate` · `note` · `password` · `file_path` · `salt` · `iv`

`occurred_at`은 클라이언트 값을 신뢰하지 않고 **서버 시각**을 쓴다. 시계 조작으로 로그 순서를 흐릴 수 없게 한다.

`target_user_id`가 이 원칙에 어긋나지 않는 이유: 이것은 **접근 통제 메타데이터**(누가 누구에게 권한을 넘겼는가)이지 연봉 데이터가 아니다. 서버는 이미 `user_id`로 행위자를 알고 있고, `target_user_id`는 그 짝일 뿐이다. 약 2년 주기의 담당자 교체를 추적하려면 이 기록이 필수적이며, 이것이 없으면 "언제 누구에게서 누구로 넘어갔는지"를 재구성할 수 없다.

### 10.3 API

| 메서드 | 경로 | 권한 |
|---|---|---|
| POST | `/api/v1/salary/access-logs` | `SYSTEM_ADMIN`, `HR_ADMIN` |
| GET | `/api/v1/salary/access-logs` | **`SYSTEM_ADMIN` 전용** |
| GET | `/api/v1/salary/policy/check` | `SYSTEM_ADMIN`, `HR_ADMIN` — 현재 IP 대조 (§9.2.3) |
| GET | `/api/v1/salary/policy` | **`SYSTEM_ADMIN` 전용** |
| PUT | `/api/v1/salary/policy` | **`SYSTEM_ADMIN` 전용** — `owner_user_id` + `allowed_ip` |

`PUT /policy`는 성공 시 `POLICY_CHANGE` 감사 로그를 남긴다. 정책을 바꾼 사람이 누구인지가 감사의 핵심이기 때문이다.

`GET`을 `SYSTEM_ADMIN` 전용으로 두는 이유: 본인이 본인의 감사 기록을 관리하면 감사가 아니다.

요청 본문은 `{"action": "...", "record_count": 12, "target_user_id": 7}` 뿐이다. `target_user_id`는 `action == "DELEGATE"`일 때만 허용하고, 그 외 action과 함께 오면 **거부한다**(422). `user_id`는 JWT에서, `ip_address`·`user_agent`·`occurred_at`은 요청 컨텍스트에서 서버가 채운다. 클라이언트가 보낸 `user_id`는 **무시한다**.

### 10.4 전송 실패 정책

fire-and-forget + 1회 재시도. **실패해도 금고 열기·저장을 막지 않는다.**

근거: 파일은 INSA 밖에서도 열 수 있으므로 로그가 애초에 완전성을 보증하지 못한다. 로그 서버 장애로 급여 업무가 멈추는 쪽이 더 나쁘다. 이는 §2.2에 명시한 한계와 일관된다.

### 10.5 조회 화면

`SalaryAdminPage.tsx` 하나에 **IP 정책 설정(§9.2)과 접근 로그 조회**를 함께 둔다. 둘 다 `SYSTEM_ADMIN` 전용이고, "누가 열 수 있는가"와 "누가 열었는가"는 같은 자리에서 봐야 판단이 되기 때문이다. 관리자 메뉴 하위에 배치한다.

- 상단: 담당자 · 허용 IP 설정 + `[현재 접속 IP로 설정]` + 미설정 경고
- 하단: 접근 로그 목록. 필터는 사용자 · 기간 · action. **읽기 전용**
- `IP_DENIED` 행은 눈에 띄게 표시한다. 거부된 시도가 곧 이상 징후다

## 11. 에러 처리 매트릭스

| 상황 | 감지 | 처리 |
|---|---|---|
| 비밀번호 오류 | GCM 태그 검증 실패 | "비밀번호가 올바르지 않습니다". 5회 연속 실패 시 60초 대기 — **클라이언트 UX 장치일 뿐 보안 통제가 아니다.** 공격자는 파일을 복사해 오프라인에서 무제한 시도할 수 있다. 실제 방어는 PBKDF2 210,000회의 연산 비용이다 |
| 파일 손상·변조 | GCM 태그 검증 실패 | 오류 상태 ④. `.bak` 복원 제안 |
| magic 불일치 | 헤더 8바이트 비교 | "INSA 연봉 파일이 아닙니다" |
| 미지원 버전 | `version > 1` | "최신 버전 INSA에서 열어주세요". 쓰기 금지 |
| `kdfIter` 하한 미달 | `< 100000` | 파일 거부 |
| 외부에서 파일 변경됨 | 로드 시 `lastModified` 기억 → 저장 직전 재확인 | 저장 중단 + 경고. 덮어쓸지 사용자가 선택 |
| 쓰기 중 USB 분리 | write 예외 | `.bak`이 이미 있으므로 원본 손상만 알리고 복원 안내 |
| 권한 만료 (재접속) | `queryPermission` != granted | 1클릭 재승인 유도 |
| 브라우저 미지원 | `showOpenFilePicker` 부재 | 진입 시점에 "Chrome 또는 Edge에서 이용해 주세요" |
| 감사 로그 전송 실패 | HTTP 오류 | 1회 재시도. 실패해도 업무 진행 (§10.4) |
| 위임 1단계 비밀번호 오류 | 복호 검증 실패 | 2단계로 넘어가지 않는다. 파일 미변경 |
| 위임 2단계 새 비번 불일치 | 2회 입력 비교 | 재입력 요구. 파일 미변경 |
| 위임 2단계 취소·5분 초과 | 사용자 조작 / 타이머 | 파일 미변경 + 잠금(②). 1단계 검증은 아무것도 쓰지 않았다 |
| 위임 중 재암호화 실패 | write 예외 | `.bak`은 **옛 비밀번호로 암호화된 직전 원본**이다. 전임자 비밀번호로 복원 가능함을 안내 |
| dirty 상태에서 위임 시도 | dirty 플래그 | 위임 시작 차단. "먼저 저장하세요" (§8.1.3) |
| 후임자에게 연봉 메뉴 권한 없음 | 후임자 역할 조회 | 위임은 성공 처리. 경고 배너 + 관리자 화면 링크 (§9.1) |
| 허용되지 않은 IP에서 접속 | `GET /policy/check` → `allowed: false` | 비밀번호 입력란을 렌더링하지 않음. 현재 IP 표시 + `IP_DENIED` 기록 |
| 정책 미설정 | 정책 행 없음 | **허용**한다. 관리자 화면에 상시 경고 (§9.2.4) |
| IPv4/IPv6 표기 불일치 | 정확 문자열 비교 실패 | 같은 PC라도 `::1`과 `127.0.0.1`처럼 다르게 보일 수 있다. 거부 화면의 현재 IP를 그대로 등록하게 유도 |
| VPN·재택 접속 | IP 불일치 | 의도된 차단. 필요하면 관리자가 정책을 바꾼다 |
| `policy/check` 호출 실패 | 네트워크·서버 오류 | **잠금 해제를 막지 않는다.** 서버 장애로 급여 업무가 멈추면 안 된다(§10.4와 같은 판단). 경고만 표시 |

## 12. 테스트 전략

### 12.1 `crypto.ts` 단위 테스트 (Vitest, Node webcrypto — 브라우저 불필요)

| # | 검증 |
|---|---|
| 1 | 왕복: `encryptVault` → `decryptVault` = 원본 |
| 2 | 틀린 비밀번호 → 복호화 실패 |
| 3 | **같은 평문·같은 비밀번호로 2회 암호화 → 암호문이 서로 다름** (IV 재사용 방지) |
| 4 | 암호문 1바이트 변조 → GCM 태그 검증 실패 |
| 5 | 헤더의 `iv` 1바이트 변조 → AAD 불일치로 실패 |
| 6 | magic 불일치 · 미지원 버전 · `kdfIter` 하한 미달 감지 |
| 7 | 빈 `records` 배열 왕복 |
| 8 | 비밀번호 변경: 새 비밀번호로 재암호화 후 **salt가 바뀌고**, 옛 비밀번호로는 복호 불가 |

### 12.2 `vault.ts` (FileSystemFileHandle 모킹)

- `.bak` 생성이 원본 덮어쓰기보다 **먼저** 일어난다
- 쓰기 중 예외 발생 시 원본이 보존된다
- `lastModified` 변화로 외부 변경을 감지한다
- IndexedDB 핸들 저장·복원

### 12.3 `SalaryPage.tsx` (Vitest + RTL)

- 4개 상태가 각각 올바르게 렌더링된다
- **잠긴 상태에서 금액 문자열이 DOM에 존재하지 않는다**
- 10분 자동 잠금 (fake timers), 30초 전 경고
- dirty 상태 이탈 시 경고
- 역할이 없는 사용자에게 메뉴가 보이지 않는다

### 12.3.1 위임 흐름 (§8.1)

- 1단계 비밀번호가 틀리면 **2단계로 넘어가지 않는다**
- 2단계에서 취소하면 `writeVault`가 **호출되지 않는다** (파일 미변경)
- 2단계 화면에 1단계 입력값이 남아 있지 않다
- 위임 완료 후 상태가 **②(잠김)**으로 전환된다
- 위임 모달이 열린 동안 10분 자동 잠금이 발동하지 않는다 (fake timers)
- 모달 5분 초과 시 취소 + 잠금
- dirty 상태에서 `[담당자 위임]`이 비활성이다
- 후임자에게 연봉 역할이 없으면 경고 배너가 뜬다

### 12.3.2 IP 제한 화면 (§9.2)

- `allowed: false`면 **비밀번호 입력란이 DOM에 없다**
- 거부 화면에 현재 IP가 표시된다
- `policy/check` 호출이 실패해도 잠금 해제가 막히지 않는다
- 관리자 화면의 `[현재 접속 IP로 설정]`이 `currentIp`를 입력란에 채운다

### 12.4 백엔드 (pytest)

- 역할 없는 사용자 POST → 403
- `HR_ADMIN`의 GET → 403 / `SYSTEM_ADMIN`의 GET → 200
- 로그 생성 시 `user_id`·`occurred_at`을 **서버가** 채운다 (클라이언트 값 무시)
- **응답 스키마와 ORM 모델에 §10.2 금지 필드가 존재하지 않는다** (회귀 테스트)
- `DELEGATE`는 `target_user_id`를 저장한다
- `action != "DELEGATE"`인데 `target_user_id`가 오면 **422**
- 존재하지 않는 `target_user_id` → 400

### 12.4.1 IP 정책 (§9.2)

- 요청 IP가 `allowed_ip`와 같으면 `allowed: true`
- 다르면 `allowed: false` + `IP_DENIED` 로그가 남는다
- **정책 행이 없으면 `allowed: true`** + 미설정 플래그 (§9.2.4)
- `PUT /policy`는 `SYSTEM_ADMIN`만 (`HR_ADMIN` → 403)
- `PUT /policy` 성공 시 `POLICY_CHANGE` 로그가 남는다
- 잘못된 IP 형식 → 422
- `X-Forwarded-For`가 있을 때 **nginx가 아니라 실제 클라이언트 IP**를 쓴다 (`--proxy-headers` 전제)

### 12.5 커버리지

프로젝트 규약대로 70% 이상. `crypto.ts`는 **90% 이상**을 목표로 한다.

## 15. 운영 규칙 (기술로 강제 불가 — 문서·교육으로 보완)

1. `salary.enc`는 **반드시 USB에만** 저장한다. 브라우저는 저장 위치를 확인할 수 없다.
2. USB는 사용하지 않을 때 분리해 잠금 보관한다.
3. 비밀번호는 인사팀 책임자가 별도의 안전한 곳에 보관한다. **분실 시 복구 불가.**
4. USB는 정기적으로 별도 매체에 복제한다. `.bak`은 같은 USB에 있으므로 매체 분실에는 무력하다.
5. **담당자 교체 시 반드시 `[담당자 위임]`을 사용한다**(§8.1.2). 전임자가 새 비밀번호를 대신 정해 알려주는 방식은 금지한다 — 그러면 전임자의 접근이 끊기지 않는다.
6. 위임은 전임자와 후임자가 **같은 자리에 함께 있을 때** 수행한다. 2단계는 후임자가 직접 입력해야 한다.
7. 위임 직후 후임자가 새 비밀번호로 파일이 열리는지 **그 자리에서 확인**한다. 화면이 자동으로 잠기는 이유가 이것이다.
8. 위임 후 관리자 화면에서 후임자에게 연봉 메뉴 권한을 부여하고, 전임자에게서 회수한다(§9.1 — 자동화되지 않는다).
9. **연봉 담당자 PC에는 고정 IP를 할당한다.** DHCP로 IP가 바뀌면 담당자가 금고를 열 수 없다(§9.2.5). 이는 기술로 우회할 수 없는 운영 전제다.
10. 담당자 PC를 교체하거나 자리를 옮기면, 관리자가 **그 자리에서** `[현재 접속 IP로 설정]`으로 정책을 갱신한다.
11. IP 제한은 **다른 자리에서의 무심코 열람을 막는 장치**이지 기술적 공격 방어가 아니다(§9.2.1). 이 점을 담당자 교육에 포함한다.
